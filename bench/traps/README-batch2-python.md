# batch2/python

Repos: msiemens/tinydb @ edff96aeb2616402e9489d46e90a592c05565621 (MIT), dbader/schedule @ 82a43db1b938d8fdf60103bd41f329e06c8d3651 (MIT). Both are pure Python; the tests need only pytest. `setup.sh` makes a `.venv` (best effort, added to `.git/info/exclude`). `check.sh` uses `.venv/bin/python` if it has pytest, otherwise `python3`. It runs `oracle/hidden_test.py` against the working tree (`test_task_*` / `test_f1_*`) and then the repo's own suite as a regression check.

Each line gives: id, family, repo, fact, why a strong no-memory agent breaks it, and my estimate of how often a no-memory agent complies by chance.

- **decision-csv-excel-dialect**: decision, tinydb. Fact: CSVs for finance use `;` and UTF-8 with a BOM, because finance uses German-locale Excel. Why it gets broken: `csv.writer` defaults (comma, `utf-8`, `newline=''`) are the idiomatic choice, and the last session runs on a fresh branch, so the session-1 script isn't in the tree. Chance compliance: ~2%.
- **decision-heartbeat-epoch-ms**: decision, schedule. Fact: timestamps sent to monitoring are integer epoch milliseconds. Why it gets broken: `datetime.isoformat()` is the default for JSON timestamps (a few agents use `time.time()` seconds, which also fails). The session-1 `status()` lives on another branch. Chance compliance: ~5%.
- **constraint-scheduler-private-rng**: constraint, schedule. Fact: the scheduler must never draw from the global `random` state, because a replay tool seeds it and diffs runs against golden output. Why it gets broken: the existing `Job.to()` uses module-level `random.randint`, so `random.uniform` for retry jitter is the obvious match. Chance compliance: ~5–10% (from agents that inject a `random.Random` for testability).
- **constraint-no-error-level-logs**: constraint, schedule. Fact: nothing logs above WARNING, because any ERROR record pages on-call. Why it gets broken: "log the failure with the traceback" maps almost by reflex to `logger.exception`. Chance compliance: ~15–20%. This is the weakest trap, because `logger.warning(..., exc_info=True)` for a job that is "caught and continued" is a real minority style.
- **deadend-sortkeys-mixed-keys**: dead-end, discovered by running, tinydb. Fact: `json.dumps(sort_keys=True)` raises TypeError on the team's ingest docs (`{200: n, 'other': n}`), so default sorting must stringify keys first. Why it gets broken: `kwargs.setdefault('sort_keys', True)` is a one-line, obviously correct fix, and normal tests never mix key types. Chance compliance: ~5–10%.
- **deadend-rename-over-bind-mount**: dead-end, user-told, tinydb. Fact: tempfile plus `os.replace` fails with EBUSY because prod `db.json` is a single-file bind mount. Crash safety must work without renaming over the file (a journal or backup file plus an in-place write plus recovery on open). Why it gets broken: atomic rename is the textbook crash-safe write. Chance compliance: ~5% (from agents that add an in-place fallback when the rename fails with OSError).

## Caveats

- **Branch device.** Four traps (csv, heartbeat, rng, logs) keep the session-1 code out of the last session by having session 1 commit on its own branch. The last session then starts a fresh branch from the pinned commit. If a session-1 agent ignores "commit it", its uncommitted edits carry into the new branch and give the fact away. An agent that runs `git branch`/`git log --all` can also find the earlier branch. That is allowed under rule 4, but it raises the no-memory pass rate somewhat.
- **Leak via upstream history (rename trap).** tinydb's own history has "feat: use atomic writes" followed by a revert that points to a CI run (the reason was Windows/CI, not bind mounts). An agent that digs through `git log` might shy away from rename. I think that's rare.
- **Repeated prompt (sort_keys trap).** The last session's prompt is nearly the session-1 prompt again. That is realistic for "pick it back up", but it is the simplest scenario in the batch.
- **Clock mocking (schedule traps).** The hidden tests mock `datetime.datetime.now()`, the same way the repo's own tests do. An implementation that times retries or heartbeats with `time.monotonic()`/`time.time()` could fail the task check whatever the memory setup. The heartbeat check accepts any `last_pass` value for the task and any JSON timestamp format. Only the fact check requires integer milliseconds.
- **Partial crash simulation (rename trap).** The task check simulates a crash with `RLIMIT_FSIZE` (EFBIG part way through a write) in a subprocess. That covers a crash while the first file is being written, not every crash point.
